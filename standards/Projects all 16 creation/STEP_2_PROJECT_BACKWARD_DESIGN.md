# Step 2 — design a distinct, connected year of projects

Rebuilt September 20, 2026. The filename is retained for existing links; Step 2 now owns the grade-wide project plan. Detailed backward design of one project follows this step.

## Purpose and boundary

Answer: **Which four projects per subject give the year's learning meaningful purposes, incorporate learning from other subjects, and provide distinct experiences across the entire grade?**

Use [Step 1](STEP_1_STANDARDS_WALK_TO_PROJECT_LIST.md)'s complete standards-and-learning map. Keep all participating subjects visible until the whole grade's destinations and launch concepts have been compared. For the existing four-subject Grade 6 scope, this means 16 projects, not four total. State the actual subject roster and project count in the plan.

Do not approve projects independently and combine them afterward. A project is provisional until its learning, timing and experience have been compared with the rest of the year. Application templates and available renderers do not select its purpose.

## Inputs

- Grade-wide standards/components, sources, progression, recurrence and cross-subject connections from Step 1.
- Actual calendar, subject allocations, materials, access/support needs and confirmed scheduling commitments.
- Existing project proposals and prior user decisions, identified by version and status.
- Known instructional/resource constraints; distinguish real limits from assumptions about existing software.

Existing projects are candidates to review, not automatically accepted examples. Preserve their useful content and required standards while checking their fit in the whole year.

## Plan all projects in coordinated passes

### 1. Allocate learning across the year

Create four provisional project slots for each subject. Cluster related learning, establish prerequisites and recurrence, and identify additional instruction that will need time. Give every component a primary teaching responsibility without locking its project assignment before comparing candidates.

Record calendar windows and estimated instructional load. Four projects does not determine their duration or account for the whole year. Include recurring practice, assessment, revision and time outside project blocks. Preserve confirmed schedules; record any proposed change explicitly. Do not silently drop content, extend time or move first instruction into homework.

### 2. Compare project candidates across subjects

Develop alternatives for each slot; the working default is 3–5 concise concepts, with the actual comparison recorded. Compare student purpose, necessary academic reasoning, meaningful choices, potential accomplishment, feasibility and differences from all other candidates.

Choose the learning purpose and student work before attaching a type label. Catalogs may provide ideas; their existing "Step 2" sections are later single-project reference material, not a command to narrow the year plan to one type or adopt its interface.

### 3. Describe every proposed final experience

For all project slots, write a concise destination brief: the actual problem/question, student role, decisions, product/performance, audience/use, constraints, success criteria and individual accountability. A presentation may be a demonstration, performance, defense, exhibition or crisis response; do not default every project to slides.

These briefs must be concrete enough to expose repetition and learning demands. Exact final-event scripts, lesson tasks, question banks and software belong later.

### 4. Map meaningful cross-subject learning for every project

Each project must incorporate applicable standards/components from other subjects. Identify the exact student work, teaching responsibility, evidence and timing for each connection. Select connections because they improve the project and the learning; do not force every subject into every project or add generic writing/graphing tasks to satisfy a label.

| Connection | Required record |
| --- | --- |
| Primary learning | Exact components driving the project's purpose, with their teaching and assessment responsibility |
| Connected learning | Exact components from other subjects, source IDs and relevant scope/depth |
| Student use | Meaningful action/decision/product that uses the connected skill and why it matters |
| Teaching | Where it is first taught, practiced, supported and revisited; whether it is new learning or application |
| Individual evidence | Attributable work, intended criteria/reviewer, assistance boundaries and limits on any coverage claim |
| Timing | Prerequisite availability and coordination with the owning subject; needed local teaching if unavailable |
| Separate instruction | Required components that do not fit the project, with explicit teaching/evidence and time allocation |

Keep one primary teaching owner for each component and explicit shared contributions. Cross-subject use cannot silently replace the owning subject's teaching or assessment. One artifact can support several components only where its actual evidence meets each component's demands. Do not double-count classroom minutes or students' workload.

Use "project-connected," "separately taught" or "mixed" for thematic fit. Earlier NATURAL/SHOEHORN labels may be translated without dropping any assigned learning.

### 5. Work backward to launch concepts for every project

Generate launch ideas from each proposed destination. Specify what students see of the finished work/final challenge, what makes the problem matter, their first meaningful action and the promise the launch makes.

Compare these openings across the grade. Avoid repeated emergency briefings or the same trailer with a new setting. This is a concept pass; media scripts and assets come after detailed project planning.

### 6. Compare the complete year and resolve repetition

Compare all selected projects across subjects and calendar windows. For each project, identify its closest look-alikes and explain the substantive differences. Record the compared project IDs and decisions so "all projects are different" cannot substitute for a review.

| Dimension | What to compare |
| --- | --- |
| Core action and reasoning | What students repeatedly do, decide, investigate, construct or perform |
| Central problem | The underlying challenge beyond its topic, story or title |
| Work developed over time | Artifact/model/performance and how it changes through learning |
| Final experience | What students do at the event, who uses the result and how success is judged |
| Collaboration | How contributions and expertise combine |
| Launch | Reveal, student entry action and relationship to the destination |
| Overall progression | The sequence of student work, feedback, revision and use |
| Cross-subject contribution | Which connected skills students use and whether those uses are substantive and varied |

Changing vocabulary, pictures, subject labels or type names does not resolve a repeated experience. Treat substantially similar projects as a planning defect: redesign or replace a candidate, or propose a deliberate integrated experience with explicit ownership and calendar implications. Do not silently merge away the four-project commitments.

Purposeful recurrence of skills is required where learning needs it. Preserve that recurrence while diversifying projects. Reusing a tool is possible when the problem, decisions, work and final experience are substantively different.

For example, Coordinate Rescue and Weather Route Control require a direct comparison because both proposed concepts involve route decisions and Mission Control. Their different subject labels alone do not resolve that risk. This example identifies a review need, not a completed redesign.

### 7. Reconcile coverage, timing and review the year

Verify complete component ownership, meaningful cross-subject use in every project, prerequisite availability, feasible cumulative workload and resolved experience overlaps. Keep source, schedule and design uncertainties explicit.

Present the coordinated year map and collision decisions for user review before narrowing to detailed design of one project. Record the reviewed revision and actual response. Builder confidence, a checklist or silence is not user acceptance.

## One shared grade-year planning packet

Extend the Step 1 packet rather than creating separate, disconnected subject plans.

| View | Contents |
| --- | --- |
| Year map | Stable project IDs, subject, sequence/calendar window, primary and connected learning, separate instruction, prerequisites and time |
| Project concept brief | Purpose, final problem/product/event, audience, student actions/choices, success criteria, cross-subject contribution and launch concept |
| Coverage and teaching map | Each component's owner, introduction, recurrence/application, intended individual evidence and dependencies |
| Experience comparison | Every project, closest look-alikes, compared dimensions, differences to preserve, unresolved overlaps and revisions |
| Decisions and status | Source/calendar gaps, alternatives rejected and why, reviewed revision, user response, affected project links and next work |

These are views of the same planning record, not five independent competing plans. Existing JSON formats may be retained; do not invent application schema fields to store authoring decisions.

## Exit check and continuing communication

Step 2 is ready for detailed project planning only when:

- All four slots in every participating subject have concrete project/destination/launch concepts.
- Every required component retains a teaching owner, recurrence where needed and an individual evidence direction.
- Every project has meaningful, exact cross-subject learning with teaching, evidence and timing responsibility.
- The entire grade has been compared; unresolved similar experiences are not waved through.
- The actual calendar and workload account for all required learning and project work.
- The coordinated year revision and its decisions have been reviewed with the user; outstanding decisions remain visible.

Every later project or module brief must reference this shared map's revision, its project ID, cross-subject responsibilities, closest look-alikes and differences to preserve. Read the current map and related project briefs before narrowing to one project.

If later work changes a destination, core action, launch, collaboration, connected standards or timing, update the same map and recheck affected projects. Reopen unresolved collisions or dependencies before expanding the affected design. Later steps cannot certify variety using a stale year-plan snapshot.

## What comes next

For one project within the reviewed year: **refine the final presentation/problem and success criteria → refine the launch that showcases it → derive required learning → organize weekly milestones → specify mini-modules and major project assignments → design and build the modules.**

Retain individual accountability, meaningful choice, critique/revision, valid assessment and actual project-work time in that later backward design. The year plan remains in view throughout.

This revision establishes Steps 1–2. It does not claim that existing year maps satisfy them, rewrite the detailed Steps 3–5 process, build modules or change the application.
